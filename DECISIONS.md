## n2: Analytics engine (BatteryCore/Analytics) — public API for the UI node
- **Did:** Built the analytics layer as 7 files under `Sources/BatteryCore/Analytics/` plus 6 test files under `Tests/BatteryCoreTests/Analytics/`. No existing BatteryCore file and no Package.swift was touched. `swift build` clean, `swift test` 97/97 green (29 pre-existing + 68 new).
- **Interfaces:** Entry point is `struct Analytics(store: SQLiteStore, options: AnalyticsOptions)` or `Analytics(readOnlyPath:options:)`. Queries, all taking an explicit `TimeWindow`: `drainSeries(window:bucket:) -> DrainSeries`, `topProcesses(window:limit:) -> [ProcessUsage]`, `categoryBreakdown(window:) -> [CategoryUsage]`, `batteryHealth(now:) -> BatteryHealth?`, `insights(window:) -> [Insight]`, and `report(window:processLimit:) -> AnalyticsReport` which returns all five from ONE pass — the UI should call `report` rather than the five queries back to back. `TimeWindow.lastHour/last6Hours/last24Hours/last7Days(ending:)`; `Bucket.minute/.../day` and `Bucket.auto(for:targetPoints:)`. Chart types: `DrainPoint` (percent/pctPerHour/watts are OPTIONAL — nil means no measurable discharge in that bucket, draw a hole not a zero) and `SleepGap` (shade these). `Insight` has id/severity(.info/.notice/.warning/.critical)/title/detail/score, pre-sorted most severe first. `InsightThresholds` and `AnalyticsOptions.timeZone` are settable (timeZone drives "after 2 PM" strings).
- **Adjustment (deviates from the node brief):** the brief asked for SQL `GROUP BY` aggregation in `StoreQueries.swift`. `SQLiteStore` keeps `db`, `prepare`, and `exec` `private`, so a cross-file extension cannot issue SQL, and Store.swift was off-limits to me. `StoreQueries.swift` is still an `extension SQLiteStore` and still collapses samples before attribution, but in one linear Swift pass over the existing public fetch API. Verified at full scale: a 7-day window over ~10k battery + ~20k process rows produces a complete report in well under a second (`AnalyticsScaleTests`).
- **Units caveat the UI must surface:** macOS gives a unitless per-process *energy impact* score, never joules. Per-app watt-hours and battery-percent figures are the measured battery discharge apportioned by energy-impact share — real rankings, estimated magnitudes. `ProcessUsage.estimatedWh` / `.estimatedPercentPoints` are named to say so; label them as estimates in the UI.
- **Follow-ups:**
  - Expose SQL-level aggregation from SQLiteStore [out of lane] — if windows ever grow past ~7 days, add `GROUP BY` fetches inside Store.swift and point `StoreQueries` at them; the current pass is linear but reads every row.
  - Helper-merge table is heuristic [in lane, low priority] — `AppNameNormalizer` strips ` Helper*`, maps `com.apple.WebKit.*` and `Safari Web Content` to Safari, and drops role parentheticals. Unusual apps that legitimately end in "Helper" will merge into a shorter name.
